# Watercooler

Polymarket-style play-money prediction market for coworkers. UI copy is Chinese; code and comments are English.

## Commands

- `pnpm dev` — server (:3000, tsx watch) + web (:5173, proxies `/api`)
- `pnpm test` / `pnpm typecheck` / `pnpm format` — run all three before committing
- `pnpm seed --reset` — recreate `data/watercooler.db` with demo data (xiaoming / demo123)

## Layout

- `packages/shared` — pari-mutuel pool math (`pool.ts`), API DTO types, zod request schemas. Imported as TS source by both apps.
- `apps/server` — Hono API under `/api`; `routes/*` are thin, logic lives in `services/*`. Serves `apps/web/dist` in production.
- `services/exchange.ts` — optional `polymarket` markets: Yes/No, or multi-outcome (`markets.neg_risk`, 3+ options) where every option has its own Yes (token 0) and No (token 1) share and book; binary markets only use token 0 of their Yes and No options, and the API's `token: 'no'` on an option maps to the complementary share. Integer-cent prices, whole shares, price/time matching (direct transfer and complementary mint/merge), 1 unit collateral per complete set; multi-outcome collateral is shared across options and `convertShares` turns No shares into cash plus the other options' Yes. Books are shown merged with complementary orders (Polymarket style); the displayed price is the midpoint, or the last trade when the spread is over 0.10. Order types: GTC, GTD (`expires_at`, released by `expireExchangeOrders` and never matched after expiry), and FOK/FAK, which never rest: they are planned with `planFill` (`packages/shared/src/exchange.ts`, also used for browser previews) and buys escrow exactly what the fills cost, optionally spending an `amount` in whole shares. Buy orders escrow cash; sell orders reserve shares. Positions keep an average-cost basis (`cost`) for display (avg price, value, P&L) — never for rankings. Polymarket markets cannot be cancelled manually or automatically; only unfilled orders can be cancelled. Keep existing pool mode unchanged. All cash mutations use the ledger and all exchange operations run in SQLite transactions.
- Polymarket mirror (`mimic` flag, default on, only with `polymarket` on): `mimic/sync.ts` copies polymarket.com's top K events by 24h volume (`settings` `mimic.topK`, default 50) into Polymarket-mode markets with `markets.mimic_id` (single-market events become binary markets of its two outcomes; multi-market events become `neg_risk` markets, at most 12 quoted options), every 5 minutes through `mimic/client.ts` (Gamma + CLOB, overridable with `POLYMARKET_GAMMA_URL`/`POLYMARKET_CLOB_URL`; tests use `fakePolymarket`). People trade mirrors in `services/mimic.ts` against the site (ledger `buy`/`sell`) at the live CLOB book, walked with `planFill` in whole shares at cents rounded against them, so their trades never move Polymarket; no resting orders, splits or conversions. Each option settles at Polymarket's final price (1/0/0.5) through the ledger; with the flag off a pass still settles mirrors people hold. Mirrors are created by a bot account (`settings` `mimic.creator`, see `systemUser`) that is not an AI bot (those are the `ai_bot_` usernames) and never ranks. Mirrors sit in their own zone (`zone=mimic`), never in the people's lists.
- `/api/trading/*` — programmatic trading routes using the same session auth and exchange services. Preserve user-scoped `clientOrderId` idempotency, cursor pagination, and outcome-relative fill prices. `sdk/python` is the standard-library-only Python client; `pnpm test:python` runs its unit tests and isolated real-HTTP integration test.
- `postOnly` rejects an incoming order before any fill if ordinary matching finds a counterparty (including complementary mint/merge). Roll back reservations and insertion atomically; resting post-only orders can fill later as makers. Include the flag in client-order idempotency comparisons, like the order type, share, amount and expiry. Python uses `post_only=True`; `market_order` covers FOK/FAK.
- Reject any new order that crosses the user's own open orders, including equal prices and complementary mint/merge, before reserving assets or filling against anyone. Keep the old orders intact and include the conflicting order ID in the 409 error. Idempotent retries return the original order before this check.
- `apps/web` — React SPA; pages in `pages/`, data via TanStack Query (`lib/api.ts`). Theme tokens in `src/index.css`: light in `@theme`, 黑夜模式 overrides in `html.dark` (toggled by `lib/theme.ts`).

## Conventions

- DB money columns (balances, bets, pools, pots) are INTEGER cents; the API exposes currency units (`fromCents`/`toCents`).
- Every balance change goes through `adjustBalance()` inside a transaction so it is recorded in `ledger`.
- Rankings recognize only net ledger cash flow from resolved/cancelled markets. `netWorth = funded + profit` is book value, never a quote-based estimate; `staked = netWorth - balance` is unresolved net cash investment (including order escrow), which can be negative after sales/merges. Even fully exited trades wait for market resolution before contributing to profit.
- Schema changes: append a new entry to `apps/server/src/db/migrations.ts`; never edit shipped ones.
- Mutating endpoints are POST with a JSON body (CSRF guard in `app.ts`).
- Admins (`users.is_admin`) run the instance at `/admin` (`routes/admin.ts`, `services/admin.ts`): feature flags in `settings` (`aiBots`, `wecom`, `polymarket`, `mimic`, `werewolf`), configuration (`services/instanceConfig.ts`), online restart through the control script (`CONTROL_SCRIPT`, see `controlScriptRestart`), balance adjustments (ledger kind `grant`, counted as funding like signup and bonus, so profit and rankings are untouched) and appointing other admins (never themselves away). Every admin action is written to `admin_audit`. Every `/api/admin/*` route calls `requireAdmin`. The first admin is made on the server with `<instance>.sh make-admin <username>`. Admins have no say over markets.
- Feature flags alone decide what runs; credentials never switch a feature on or off. `aiBots`, `wecom` and `werewolf` need credentials from `bot.json` and can only be switched on when the running instance has them (otherwise the switch is disabled and the API answers 409); on without them is shown as misconfigured. Missing `aiBots`/`wecom` flags are seeded once from whether `bot.json` had the credentials (`seedFeatureFlags`), `polymarket` defaults on. Flags apply at once; configuration does not: admins edit `bot.json` (model and WeCom credentials) and the site settings in `.env` at `/admin`, which only writes the files (secrets come back only as hints), and the process reads them at its next start. `restartNeeded` compares the files with what the process started with.
- Creators publish results for their own markets and may bet in them like anyone; only pool markets allow creator cancellation. `closeAt` stops trading and releases open orders; `settleAt >= closeAt` (defaults to closeAt for older clients) is the earliest resolution time for Polymarket markets; pool creators may resolve any time, which stops betting at once. Pool markets automatically cancel and refund 7 days after settleAt without a result (`cancelOverdueMarkets`). Polymarket markets cannot be cancelled manually or automatically and retain positions and collateral indefinitely until the creator publishes a result. Forgotten passwords: `src/cli.ts reset-password`.
- Betting is pari-mutuel: winners split the whole pot pro-rata (`splitPot`), nobody backing the winner means full refunds, the house never adds money. Payout previews in the browser must use the same `pool.ts` helpers the server settles with.
- AI bots (`apps/server/src/bots/`) run while the `aiBots` flag is on, with the credentials in `bot.json` (`BOT_CONFIG`, see `bot.example.json`); `runtime.ts` starts and stops them and the WeCom bot and reads `bot.json` once, at startup. They are `users.is_bot` accounts that may only bet on `markets.is_ai` markets (enforced in `placeBet`), stay off the leaderboard and site stats, and talk to the Anthropic Messages API through `@anthropic-ai/sdk` with the web search tool (`bots/llm.ts`): one search per bet, several for writing and settling questions. Question writing is the costly call and is capped per 24h in `bot_attempts`, failed attempts included. Tests use a fake `Ask`, never the real API.
- AI werewolf (狼人杀, `apps/server/src/werewolf/`) runs while the `werewolf` flag is on (default off) and needs the `bot.json` model credentials; its `werewolf` section sets `players` (6–12, default 9), `restMinutes` (default 10) and an optional cheaper `model`, editable at `/admin`. A self-contained module: one loop (`service.ts`) deals a table, waits out the break with the next game's bets already open, plays it, repeats; players are LLM calls (`createPlay`), not user accounts. `rules.ts` is the pure game (预女猎 board, 屠边 or parity for the wolves); `engine.ts` records every step as a `werewolf_events` row and replays recorded steps instead of asking again, so a restart or flag-off only pauses and resumes; market effects are written in the same transaction as their event. Its bets are pool markets (`markets.werewolf_game_id`, `werewolf_seat`) created and settled by a judge system account: the winning side (好人/狼人) and, per seat, 出局/存活 (settled the moment the player is out). Betting on all of them stops once at most `werewolfCutoff(n) = ceil(n/2)` players are alive. Roles, night actions and thoughts never leave the server before the game ends (`gameDetail`), and nothing may hint at them: the board text lists roles in a fixed order, shown events are numbered in order (database ids would count the hidden night steps by their gaps), and every night lasts at least `nightMs` (its length would count the living wolves, seer and witch). Its markets and bets stay out of every other list, feed and site stat, and WeCom neither shows, bets on nor posts about them. Tests use a fake `Play`.
- The WeCom (企业微信) bot (`apps/server/src/wecom/`) runs while the `wecom` flag is on and `bot.json` has a `wecom` section (only the watercooler instance's does). It talks to WeCom through `WecomTransport` (`connectWecom` wraps `@wecom/aibot-node-sdk`; tests use a fake), works in group chats only, and answers people without a binding with a single-use link to `/bind/:token` and nothing else — they never reach the model. Bound people chat with the bots' model through the tools in `wecom/tools.ts`; anything that moves money (bet, create, resolve, cancel, Polymarket orders and order cancellations) only creates a `wecom_actions` row and a confirmation card that its owner must tap. Polymarket market orders from a card are bounded by the worst price the card previewed; mirror orders (`mimic_order`) preview the last synced quote, are capped two cents beyond it, and run through `executeMirrorAction` (async: it fetches the live book). `wecom/notifier.ts` posts settlements and creator reminders to each person's last group, once per `wecom_notices` row. WeCom userids are encrypted strings: never show them in bot messages or pages, refer to people by their site display name.
- UI follows the 非凸科技 (ft.tech) look: light surfaces, brand blue, 4px buttons, underline tabs. Use theme tokens (`bg-panel`, `text-fg`, `border-line`, `text-brand`, …), never hard-coded colours, so 黑夜模式 keeps working; SVG colours go through `style={{ stroke: 'var(--color-…)' }}` or `useThemeColor()`.
- Every page sets its browser tab title with `usePageTitle()` (`lib/site.ts`): "页面 · SITE_NAME", the home page keeps index.html's.
- `useEffect` callbacks use block bodies and only ever return a cleanup function: `useEffect(() => x(), …)` returns `x()`'s value, which React later calls as the cleanup (this crashed production when a browser's `window.scrollTo` returned a value).
- The app may be served under a sub-path (`BASE_PATH`, e.g. `/watercooler` in production). Never hard-code root-relative URLs in the web app: use router links/`navigate()` (router has a `basename`) and `import.meta.env.BASE_URL` for anything else.
- Deployment: `.github/workflows/deploy.yml` + `deploy/` (remote activation script, `watercooler.sh` start/stop/restart script, setup guide). The same code runs as independent instances (`watercooler`, `gang-bet`), each with its own `~/<instance>` dir, port, `BASE_PATH`, `SITE_NAME`, `SITE_COPY` and database; they are listed in the workflow's `matrix.include`. Instance-flavoured UI copy (anything mentioning 茶水间/同事) goes in `apps/web/src/lib/site-copy.ts`, read via `COPY` from `lib/site.ts`, never inline.
